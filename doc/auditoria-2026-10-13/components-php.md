# Componentes PHP: shared, Core y App

## Resumen

La capa de componentes tiene una idea sólida (clases PHP con named args que devuelven HTML, TableComponent model-driven, DTOs tipados, auto-discovery por `#[ApiComponent]`) enterrada bajo mucho código que nadie usa y varios "una sola forma" rotos. De 40 PHP en shared/, 25 no tienen ningún uso fuera de sus barrels/docblocks (Forms completos salvo InputText/TextArea/Select/FilePond, todos los Essentials de layout, ImageGallery, 6 de 7 Renderers); los 4 barrels con class_alias + 4 _ide_helper + generador + hook de composer tienen cero consumidores. ScreenComponent nunca se instancia: los 15 módulos copian su HTML a mano. Un CRUD de 5 campos (ExampleCrud) cuesta 17 archivos y ~3.760 líneas, con registro manual en Core/Config/MenuStructure.php y routeMap.json; los seis módulos de App no comparten estructura (UsersConfig sin Edit y su botón Editar abre una ruta inexistente; dos formas de leer el id; example-form.css copiado 7 veces en 3 variantes). Hay fallos reales: inputs y selects sin escapar (XSS almacenado vía nombres de grupo), onclick de MenuConfig con route sin escapar, Renderers que emiten Tailwind cuando el layout SPA no lo carga, FilePond imprimiendo "required" como texto, valueFormatter "date" y filterType "boolean" que no existen. PHP emite JS como string por cuatro vías distintas (JS_PATHS, JS_PATHS_WITH_ARG, `<script>window.X=json`, onclick) y los "módulos" se cargan con fetch+new Function, no como ES modules. MakeComponentCommand genera un componente que no se parece a ningún módulo real. Para Lego 2: conservar CoreComponent+DTOs+model-driven, reescribir Screen/Table/Forms mínimos con escape por defecto, y descartar el 60% restante.

## Lecciones

- Lo que funcionó y debe sobrevivir: una clase PHP por componente con named args y `component(): string`, DTOs readonly (ColumnDto, MenuItemDto) con colecciones variádicas tipadas, y `TableComponent(model: X::class)` apoyado en `#[ApiGetResource]`: ese trío ya es, en pequeño, el módulo declarativo que el dueño quiere. El auto-discovery por `#[ApiComponent]` demostró que registrar rutas a mano es innecesario.
- Construir 'shared' antes de necesitarlo produce muertos: 25 de 40 PHP de shared/ no tienen ningún uso (Essentials de layout, 7 de Forms, 6 de 7 Renderers, ImageGallery). Regla para Lego 2: un componente compartido nace cuando el segundo módulo lo necesita, nunca antes.
- Una sola fuente de verdad o ninguna: las constantes SCREEN_*, la tabla menu_items, MenuStructure.php y SCREEN_CONFIG en JS repiten los mismos ids y rutas; el resultado es que UsersConfig abre una pantalla que no existe sin que nada falle en compilación. La identidad del módulo debe declararse una vez y propagarse por el núcleo con un test que lo compruebe.
- PHP que emite JavaScript como string (renderers, onclick, `<script>window.X = json`, `new Function` para cargar módulos) es la fuente de los 231 globales y de que Tailwind aparezca donde no está cargado. El contrato PHP→JS debe ser datos (`data-*`/JSON) y módulos ES reales, nunca código.
- Los componentes nacieron para contenido fijo y por eso nadie escapa nada; en cuanto reciben datos de BD (nombres de grupos, rutas de menú) aparece XSS. Escapar por defecto en la base es más barato que auditar 65 heredocs.
- Copiar un módulo para hacer otro (Example → Tools → Users → Roles → AuthGroups) multiplica el CSS (7 copias de example-form.css en 3 variantes) y bifurca el patrón en cada copia. Si crear un módulo cuesta 17 archivos, la gente copia; si cuesta 3, no.
- El wrapper obligatorio (ScreenComponent) solo funciona si el núcleo lo aplica; dejarlo como opción hizo que los 15 módulos lo copiaran a mano. Lo que es obligatorio se impone en la clase base o en el router, y un test de arquitectura lo vigila.
- Las herramientas de DX que no resuelven un dolor real (barrels + IDE helpers + generador + hook de composer para ahorrar `use`; make:component desalineado del patrón) terminan sin usuarios y con costo de mantenimiento. Un generador solo vale si produce exactamente lo que el repo ya hace.
- Los READMEs dentro de components/ quedaron describiendo módulos anteriores (ProductsCrudV3) y rutas inexistentes: la documentación debe vivir en un solo lugar (doc/) y, donde sea posible, derivarse o validarse contra el código.

## Preguntas de diseño

- Tabla: ¿seguir con AG Grid (potente, pero 771 líneas de glue, callbacks por window y renderers que generan JS) o una tabla HTML propia renderizada en servidor con orden/filtro/paginación por query string y un módulo JS mínimo? La respuesta decide qué pasa con ColumnDto, RowActionDto y los renderers.
- Pantallas Create/Edit: ¿son componentes/ventanas separados que se abren como 'módulos abiertos' (como hoy, con una ventana Edit única reutilizable), o un solo componente de formulario con modo crear/editar y el id como parámetro? Define cuántos archivos tiene un módulo y qué significa 'módulo abierto'.
- Fuente de verdad del menú: ¿se deduce del código (atributo en la clase del módulo: ruta, label, icono, padre) y la BD guarda solo orden/visibilidad/roles editables, o la BD es completa y editable (MenuConfig) y el código solo declara rutas? Hoy conviven ambas y el seed manual (MenuStructure.php) es el puente.
- ¿Entra la subida de archivos al núcleo? Si MinIO sale, ¿disco local + tabla de archivos como parte del módulo declarativo (campo tipo 'file'), o la subida queda fuera del núcleo y FilePondComponent/ImageGallery desaparecen?
- ¿Qué componentes de formulario 'ricos' merecen estar en el núcleo? Select con búsqueda/grupos y multi-selección implica JS propio; la alternativa es `<select>` nativo + CSS y dejar lo rico como extensión opcional del portafolio.
- ¿Se conserva el render de componentes PHP desde JS por API (DynamicComponentInterface + ComponentRegistry + ComponentsController)? Hoy solo IconButton lo implementa y exige bootstrap manual; si la respuesta es no, todo ese subsistema sale.
- Login y layout principal: ¿son componentes PHP que devuelven el documento HTML completo (como hoy, en heredoc) o existe una plantilla de documento del núcleo con slots, y Login/Main son solo contenido? Afecta a cómo se declaran assets globales y a si se permiten CDNs.
- Renderers de celda: ¿clases PHP que producen JS (modelo actual) o tipos de columna declarativos (bool, date, money, badge) que el JS de tabla formatea sin eval y con CSS propio? La segunda opción elimina la generación de código pero limita la personalización.
- MenuConfig (3.425 líneas): ¿forma parte del núcleo de Lego 2 o es una herramienta opcional/portafolio? Si el menú se deduce del código, su alcance se reduce a orden, visibilidad y roles.
