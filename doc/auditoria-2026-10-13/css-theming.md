# CSS y sistema de temas

## Resumen

El sistema de temas tiene la idea correcta (paleta base -> tokens semánticos que cambian con html.dark/html.light -> componentes sin colores) pero la implementación la contradice en cada capa: hay dos archivos de tokens que se pisan (base.css gana sobre theme-variables.css con valores distintos), 171 de 329 variables definidas no se usan, 24 variables usadas no existen en ningún sitio, y cada módulo de App vuelve a definir los tokens globales con hex propios, con dos azules de acento distintos en la misma pantalla (el "ejemplo canónico" del contrato es el peor caso).

Volumen: 40 archivos CSS, 10.266 líneas (287 KB). 2.734 líneas (27%) son 9 copias del mismo CSS de formulario (5 idénticas byte a byte); ~900 líneas son código muerto verificable (windows-manager.css, automation.css, modales legacy de roles/users, variantes BEM que el PHP nunca genera); 1.003 valores px y 190 !important violan el contrato que exige rem y tokens.

Cambio de tema: funciona por clase en `<html>` sin JS en componentes (acierto), pero hay tres inicializadores distintos, la clase se duplica en body contra el propio contrato, y SweetAlert2 y AG Grid usan mecanismos paralelos. Responsive: 5 breakpoints distintos y el sidebar fijo de 15rem sin ninguna media query. Cada instancia de componente inyecta su `<link>` con cache-buster aleatorio: sin caché y hojas duplicadas en el DOM.

Los dos scripts de validación no funcionan (regex rota, lookahead inválido en grep -E, dependencia de Node sin package.json) y no hay ningún test de CSS.

Estimación para Lego 2: ~5% entra casi tal cual (screen, breadcrumb, icon-button, home, column/row y ~120 tokens), ~53% se reescribe (la idea sirve: shared forms, sidebar, header, menu-config, table) y ~41% se descarta. Una base de diseño consistente cabría en ~1.800 líneas (≈18% del tamaño actual).

## Lecciones

- Un sistema de tokens solo funciona si hay UN archivo y un test que impida definir tokens fuera de él: aquí hubo dos capas (base.css + theme-variables.css) que se pisaban, y cada módulo acabó redefiniendo los tokens con hex porque no sabía qué valor real tenía la variable.
- Los tokens creados 'por si acaso' (--button-bg-primary, --card-*, --modal-*, --z-*: 171 variables) nunca se usaron; un token se crea cuando aparece su segundo consumidor, no antes.
- El patrón de clase en `<html>` + variables semánticas funcionó: los componentes cambian de tema sin JS. Lo que dolió fue duplicarlo en body, tener tres scripts de inicialización y permitir mecanismos paralelos (SweetAlert, AG Grid). Un script inline de cinco líneas que ponga data-theme en html basta.
- Copiar el CSS del 'ejemplo' a cada módulo (9 example-form.css) es la consecuencia natural de que el framework no dé suficiente estilo desde sus componentes de pantalla y formulario: si Screen y Form no visten el módulo, el módulo copia. En Lego 2 un módulo declarativo no debe necesitar CSS.
- Los fallbacks var(--x, #hex) ocultan errores: 24 variables inexistentes pasaron desapercibidas porque 'se veía bien' con el fallback. Sin fallbacks y con un test que valide que toda var() existe.
- Los !important y los z-index de 9999999 aparecen donde el shell (sidebar, header, módulos, modales) no tiene un modelo de capas definido; los stacking contexts y la escala --z-* se deciden al principio y los modales los provee el núcleo.
- Los scripts de validación en bash/Node que nadie ejecuta se pudren (regex rotas, docs inexistentes). La validación de CSS tiene que vivir en el mismo runner que el resto de tests (Pest, test de arquitectura) o no existir.
- Inyectar un `<link>` por instancia de componente con cache-buster aleatorio fue cómodo para desarrollar pero anula la caché y acumula hojas en el DOM en una SPA que no refresca; la recolección y deduplicación de assets es responsabilidad del renderer de página.
- Las paletas mezcladas (grises y azul de Tailwind en fallbacks, #3b82f6 en módulos, #3ba1ff global, naranja para errores en inputs) aparecen cuando el código ejemplo viene de fuera; la paleta se documenta con nombres por tono y el test rechaza cualquier hex fuera de tokens.css.
- El breakpoint tiene que ser un token: con 480/640/768/769px y 48rem nada se apila igual, y el sidebar fijo sin media query hace el panel inutilizable en móvil.
- Un CSS 'de componente' que contiene selectores globales (.icon, hr, body, *) contamina toda la app; la regla de prefijo obligatorio por archivo es barata de testear y evita la mayoría de regresiones visuales.

## Preguntas de diseño

- ¿Lego 2 mantiene dark + light o solo dark? Hoy dark es el default y light arrastra bugs (colores de error, menu-close-button); cada token cuesta el doble con dos temas.
- ¿Se conservan SweetAlert2 y AG Grid con sus temas propios, o diálogos y tablas pasan a ser componentes Lego estilados con tokens? Ambos exigen hoy un mecanismo de tema paralelo y cientos de líneas de overrides con !important.
- ¿Puede un módulo de app tener CSS propio? Propuesta: no por defecto; si lo tiene, solo selectores con su prefijo y sin definir tokens, verificado por test de arquitectura. ¿Aceptas esa restricción?
- ¿Recolección de CSS en servidor (un `<link>` por archivo usado, con hash de contenido) o un único lego.css concatenado a mano que incluya los componentes shared? Ambos cumplen 'sin build', pero el primero carga solo lo usado y el segundo es más simple.
- ¿Breakpoint único (p. ej. 48rem) con el sidebar como drawer en móvil, o Lego 2 es explícitamente desktop-first y el móvil solo debe 'no romperse'?
- ¿El login comparte shell, componentes y tokens del panel (sin Tailwind), o se admite una página aparte con su propio estilo?
- ¿Fuente del sistema o Poppins self-hosted en assets/fonts? El @import a Google Fonts bloquea el render y requiere red al arrancar.
- ¿Unidades: rem puro con escala de tokens, o se permiten px explícitamente para bordes y sombras (1px, 2px)? El contrato actual prohíbe px y hay 1.003.
- ¿Qué estados visuales provee el núcleo por defecto para cualquier pantalla (loading, empty, error, no-context)? Hoy cada módulo los reinventa en su CSS.
