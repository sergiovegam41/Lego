# Núcleo: modelo de componentes, pantallas y utilidades

## Resumen

El modelo "componente = clase PHP con constructor tipado (named args) que devuelve HTML" funciona y es lo único de esta dimensión que debe sobrevivir casi intacto; renderChildren/renderSlot ya tienen tests. Alrededor hay cuatro capas que no se hablan entre sí: (1) assets resueltos por reflexión+regex, con cache busters por instancia (uniqid/time) y servidos por un symlink git que en Windows es un archivo de texto; (2) un "contexto" PHP→JS que lee `$attribute->route` (la propiedad real es `$path`) y que ningún componente invoca; (3) la identidad de pantalla repartida en `#[ApiComponent]`, constantes `SCREEN_*`, MenuStructure (433 líneas que copian esas constantes), Screens.php/ScreenRegistry (nunca cargados) y la BD; (4) un subsistema de componentes dinámicos (interface, registry, excepción, bootstrap, controller, JS) sin ningún consumidor real. Core/Models y Core/providers son relleno heredado: un query builder con SQL concatenado y 0 subclases, traits importados pero nunca llamados, enums de idioma/mensajes sin uso. De los 25 archivos revisados ninguno entra tal cual a Lego 2: 10 se reescriben conservando la idea y 15 salen. El contrato de componente está documentado en 15 archivos y doc/componentes/assets.md describe un mecanismo (módulos ES, `?v=mtime`, `/component/x/y.css`) que el código no implementa.

## Lecciones

- Los constructores con named arguments tipados + heredoc HTML (ExampleCrud, ScreenComponent, IconButton) se leen bien y son el único trozo del núcleo que gustó: Lego 2 debe conservar exactamente eso y hacer component()/render() puros (sin mutar estado, sin BD, sin globals).
- Co-localizar CSS/JS con la clase PHP y escribir './x.css' es el instinto correcto, pero resolverlo por reflexión+regex sobre el nombre del archivo y emitir `<link>`/`<script>` por instancia con busters por render produjo duplicados, caché anulada y una dependencia de symlinks: el recolector de assets debe ser de página, con un hash por archivo y un único prefijo servido igual en todos los SO.
- Pasar datos PHP→JS por `<script>` inline + fetch + new Function creó un sistema de módulos paralelo (loadModules/loadModulesWithArguments, waitForLego cada 10 ms) que impide usar módulos ES nativos; en Lego 2 los datos viajan en data-attributes o `<script type=application/json>` y el módulo se importa una vez.
- 'La BD es la fuente de verdad' convivió con constantes SCREEN_*, el atributo `#[ApiComponent]`, MenuStructure y ScreenRegistry: cinco verdades para la identidad de una pantalla. Elegir una (código, vía atributo) y dejar a la BD solo los overrides del usuario si se decide mantenerlos.
- Todo registro manual (Screens.php, RegisterDynamicComponents, MenuStructure, routeMap.json) se quedó vacío, desactualizado o nunca se cargó; lo único que se usó fue el escaneo de carpetas (ApiRouteDiscovery). Lego 2: un solo mecanismo de descubrimiento, cacheado y cubierto por test.
- Los tests existen solo donde el código es puro (renderChildren, ResponseDTO); todo lo que hace die, lee globals, consulta BD desde traits o usa time() quedó sin test. Diseñar el núcleo como funciones que devuelven strings/objetos y dejar la E/S en el borde (router/layout) es la condición para que P6 sea alcanzable.
- La documentación se multiplicó (15 archivos para el mismo contrato) y se desvió del código (assets.md describe módulos ES y `?v=mtime` que no existen). Un documento por concepto y un test snapshot del HTML emitido evitan esa deriva.
- Cada API 'híbrida' (fromModel/fromManual, dynamic/static, render/html, getParentId/getMenuGroupId, SCREEN_PARENT obsoleto-pero-implementado) dejó una mitad TODO o muerta: enviar un solo camino y borrar la alternativa en el mismo commit.
- Un identificador en español o con typo en el núcleo (isAutenticated, msj) se replica en tres capas y después ya nadie lo corrige; la revisión de nombres importa más en Core que en App.
- Los symlinks de git (public/components, public/assets) y los namespaces que no coinciden con las carpetas rompieron la paridad Windows/Linux; Lego 2 no debe depender de ningún symlink ni de case-insensitivity del sistema de archivos.

## Preguntas de diseño

- ¿Dónde vive la identidad y la jerarquía de pantallas en Lego 2: solo en código (un atributo `#[Screen(path, label, icon, parent, order)]` descubierto por escaneo) o sigue siendo editable en BD como hoy con MenuConfig? Si ambas, ¿qué guarda la BD exactamente (solo orden/visibilidad por usuario)?
- ¿Cuál es el modelo de composición canónico: arrays de children/slots estilo Flutter (ScreenComponent, FormComponent) o heredoc con `{$hijo->render()}` (ExampleCrud)? Hoy conviven; la elección determina si render() puede devolver solo HTML y delegar los assets a un recolector de página.
- ¿Debe PHP seguir pasando datos iniciales al JS del componente (hoy ScriptCoreDTO/JS_PATHS_WITH_ARG) o los módulos ES leen data-attributes y consultan la API? Define si existe un equivalente de 'script con props' en Lego 2.
- ¿Necesita Lego 2 renderizar componentes desde JS vía API (ComponentRegistry, /api/components/batch) o basta con HTML servido en /component/* + módulos ES? Hoy no hay ningún consumidor real.
- ¿La identidad de un componente se deduce estrictamente de la carpeta (Carpeta/CarpetaComponent.php, Carpeta.css, Carpeta.js, sin propiedades CSS_PATHS/JS_PATHS) o se declara explícitamente (atributo `#[Assets]`)? Afecta a la resolución de rutas, al generador make:component y a los tests de arquitectura.
- ¿Se mantiene la convención `(array) new ResponseDTO(...)` + `StatusCodes::HTTP_*` en toda la API o se pasa a un objeto Response JsonSerializable con enum HttpStatus? Son ~200 call sites en App.
- ¿Debe el núcleo conocer la librería de tablas (DimensionValue::toAgGrid, TableConfig en Core/Components/Table) o la tabla es un componente compartido fuera del núcleo con sus propios tipos y adaptador? Relacionado con la capa declarativa 'modelo + atributos → tabla'.
- ¿Qué hace un fetch de /component/* sin sesión: 302 a /login (comportamiento actual por efecto secundario) o 401 que el window manager maneja? Define la separación entre comprobar sesión y actuar.
