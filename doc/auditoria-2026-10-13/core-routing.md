# Núcleo: entrada, routing y descubrimiento de rutas

## Resumen

Flujo real de una request: `public/index.php` -> `Core/bootstrap.php` (dotenv, `session_start` sin uso, Eloquent, instancia IconButton por efecto secundario) -> `Core\Router::dispatch`, que recorta el prefijo mutando `$_SERVER['REQUEST_URI']` y hace `require` de `Routes/Api.php`, `Routes/Component.php` o `Routes/Web.php` (scripts con efectos) y por último `Flight::start()`.

Conviven SEIS mecanismos de registro de rutas que se solapan: rutas manuales Flight en `Routes/*.php`, `#[ApiRoutes]` (ApiControllerRouter), `#[ApiGetResource]` (ApiGetRouter), `#[ApiCrudResource]` (ApiCrudRouter, sin ningún modelo que lo use), `routeMap.json` legacy (`CoreController::getMymapControllers`, duplica rutas ya registradas y rompe `/api/auth/{accion}`) y `#[ApiComponent]` (ApiRouteDiscovery). A eso se suman ScreenRegistry/Screens.php (nunca se cargan) y ComponentRegistry/RegisterDynamicComponents (registro manual). Una misma URL de pantalla se declara en 4-5 sitios.

Seguridad: el chequeo de auth de `/component/*` es inalcanzable (`isAutenticated` redirige y hace `exit`), Flight imprime stack traces en 500 y 404 HTML para `/api`, las rutas de assets construyen paths sin `realpath`, y `bootstrap.php` arrastra helpers SQL por interpolación y `p()` con `die` dentro de providers de login.

Assets: hay dos pipelines (ruta PHP `/component/x/f.css` que nadie usa y alias nginx `/components/`); con `php -S` no se sirven los assets de componentes y las URLs relativas se rompen si la página termina en `/`.

Flight es reemplazable (7 archivos, ~35 llamadas); lo que de verdad ata es el `echo+die` de `Core\Response` y los `Routes/*.php` como scripts. No hay ni un test del routing. `getenv('APP_ENV')` nunca se puebla, así que todos los logs 'dev' de los routers son código muerto.

Vale la pena conservar como idea: las 3 capas (`/api` JSON, `/component` fragmento, `/` página), el atributo en la clase como única declaración y el escaneo por carpeta sin tocar archivos de rutas. Todo lo demás se reescribe o se borra.

Notas de los verificadores sobre ubicaciones corregidas:

- "serveStaticFile y las rutas de assets no validan…": reportado en Core/Router.php:90; el defecto se origina en Routes/Component.php:66-67 y 73-74. El verificador amplía: Flight aplica `urldecode()` tras el match, así que `%2e%2e%2f` permite traversal de varios niveles, no de uno.
- "Las URLs de assets son relativas…": reportado en CoreComponent.php:85; la URL relativa se genera en la línea 92 (y 96/101). Flight acepta `/admin/` como URL válida sin redirección 301.
- "Cache 'immutable, 1 año'…": reportado en Core/Router.php:116; el header de Router.php nunca se aplica a los assets reales (van por nginx/.htaccess/symlink). El único sitio donde coexisten ambos es MainComponent.php:165 con public/router.php:42. `clearCache()` no tiene llamadores.
- "Crear un módulo hoy exige 6 o más puntos…": reportado en Routes/Api.php:113 (un comentario). El punto de registro manual real es Core/Config/MenuStructure.php. El verificador matiza que `const ROUTE` y `php lego map:routes` no son obligatorios para controladores con `#[ApiRoutes]`; conteo ajustado: 5 puntos manuales reales para una pantalla, más `#[ApiGetResource]` si lleva tabla.
- "bootstrap.php arrastra helpers SQL…": el verificador añade que `p()` en los providers de auth devuelve al cliente el DTO de la petición serializado (username/password, refresh_token) antes de `die`.

## Lecciones

- Funcionó: separar en 3 capas por prefijo (/api JSON, /component fragmento HTML, / página completa). El frontend la entiende y es la base natural de 'navegar sin refrescar'. Lego 2 debe conservarla pero implementarla con un router propio, no con un hack sobre REQUEST_URI.
- Funcionó: el atributo PHP en la clase como única declaración (#[ApiComponent], #[ApiRoutes], #[ApiGetResource]) y el escaneo por carpeta. Cada vez que se usó de verdad (17 pantallas, 6 controladores, 5 modelos) eliminó un archivo de registro; cada vez que se mantuvo el mecanismo anterior en paralelo (routeMap.json, const ROUTE, MenuStructure, Screens.php) apareció una inconsistencia.
- Dolió: cada mejora se SUMÓ sin borrar la anterior. Hoy coexisten 6 formas de registrar una ruta y 4-5 lugares donde se escribe la misma URL. Regla para Lego 2: una feature nueva de routing solo entra si borra a la que reemplaza en el mismo commit.
- Dolió: sin tests del routing, los bugs silenciosos vivieron meses: ScreenRegistry nunca se carga, el atributo expone 'path' pero se lee 'route', getenv('APP_ENV') siempre es false, /api/auth/x da 500 con traza. Un test que construya la tabla de rutas desde un fixture habría detectado todos.
- Dolió: echo+die en Response y Routes/*.php como scripts con efectos hacen imposible instanciar el router en un test. Lego 2: handlers devuelven Response, el único exit está en index.php.
- Dolió: deducir el FQCN leyendo el archivo con regex en vez de usar PSR-4 (carpeta = namespace) escondió el desajuste childs/Childs, shared/Shared hasta que Linux falló y hubo que parchear con symlinks. La convención debe estar en UN lugar (composer.json) y un test de arquitectura debe fallar en cualquier SO si una carpeta no coincide.
- Dolió: 'middleware' implementado como función booleana que redirige y hace exit. Para una SPA que hace fetch de fragmentos, el 302 a /login llega como HTML dentro del módulo y obliga al JS a olfatear el login. La capa debe decidir la respuesta (401 JSON vs redirect), no el helper.
- Dolió: servir estáticos por 3 caminos (nginx alias, .htaccess, ruta PHP) con comentarios que afirman lo contrario de lo que pasa; en Windows los symlinks de public/ son archivos de texto y con php -S los assets de componentes no cargan. Un solo handler estático con realpath, o una carpeta build en public/, y nada más.
- Dolió: los nombres mienten (ApiComponent sirve HTML, /api/get/ pone un verbo en la URL, isAutenticated con typo redirige). Para un lector humano o IA, el nombre es la documentación más barata; en Lego 2 se revisa el nombre antes que el código.
- Dolió: los bloques 'FILOSOFÍA LEGO' en cada archivo describen intenciones, no comportamiento, y quedaron desactualizados (nginx.conf, index.php, Router.php, doc/routing). La doc en español debe vivir en doc/ y estar respaldada por un test, no en docblocks de 50 líneas.
- Dolió: cache-busting con time()/uniqid() en cada render junto a Cache-Control immutable de 1 año: el servidor promete inmutabilidad y el cliente la anula. Versionar por hash/mtime calculado una vez.
- Dolió: el escaneo en cada request (43 componentes + 24 controladores + 11 modelos x2, con file_get_contents y autoload de todo) no se notó porque la app es pequeña; en Lego 2 la tabla de rutas se construye una vez (cache opcache-friendly) y el escaneo en vivo queda para dev.

## Preguntas de diseño

- ¿Los fragmentos de /component/* van protegidos por la misma sesión que las páginas? Si sí, ¿la respuesta a un fetch sin sesión es 401 JSON (y el JS redirige) o el servidor emite el redirect? Hoy es un redirect con exit que el JS olfatea.
- ¿Tabla de rutas compilada a un archivo PHP por un comando CLI (rápido, pero reintroduce un artefacto generado) o escaneo en cada request con cache solo en producción? ¿Cuántos módulos se esperan como máximo (afecta si el escaneo en vivo es aceptable)?
- ¿Cada pantalla tiene URL navegable propia (/admin/tools, deep-link, historial del navegador) además del id interno? Esto condiciona cómo se representan los 'módulos abiertos' y si el router de PHP y el del JS comparten la misma tabla.
- ¿Se conserva 'renderizar un componente por id desde JS' (/api/components/batch, usado por tablas) o en Lego 2 las tablas y botones se renderizan íntegramente en PHP? Decide si ComponentRegistry/ComponentsController se reescriben o se borran.
- ¿Router propio (~150 líneas, testeable, sin dependencia) o seguir con Flight detrás de una interfaz? El coste de reemplazo hoy es bajo (7 archivos); el coste de mantener Flight es su manejo de errores y su semántica 'return truthy = continuar'.
- ¿Estilo de API para los módulos declarativos: REST (GET/POST/PUT/DELETE sobre /api/{recurso}/{id}) o acciones POST (/api/{recurso}/update)? Hoy conviven ambos presets y el frontend usa el segundo.
- ¿Entornos soportados oficialmente: solo Docker (nginx+php-fpm) y php -S para desarrollo? Si Apache sale, se borra .htaccess; si php -S es oficial, el handler estático debe vivir en PHP.
- ¿El menú se deriva al 100 % del atributo de cada pantalla (sin MenuStructure ni tabla menu_items) o el dueño quiere seguir editando el menú en BD (MenuConfig)? Si lo segundo, ¿la BD guarda solo overrides (orden/visibilidad) sobre lo que declara el código?
- ¿Los assets de componentes (CSS/JS/imágenes) se sirven desde la carpeta del módulo vía PHP (una carpeta = todo el módulo, como pide el dueño) o se publican en public/ con un paso de copia? Lo primero exige el handler estático único; lo segundo contradice 'sin build'.
