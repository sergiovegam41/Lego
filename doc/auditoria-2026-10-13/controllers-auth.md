# Controladores, autenticación y seguridad

## Resumen

Controladores y auth: Core/Controllers tiene 7 clases base de las que 3 no se usan (CoreViewController, RestfulController y la familia AbstractCrud/DefaultCrud/ApiCrudRouter: ningún modelo lleva `#[ApiCrudResource]`); App/Controllers tiene 20 archivos, 5 son CRUD copiados a mano (1.925 líneas con normalizeId y formatBytes duplicados) y 6 son stubs o demos (grupo auth "api", login_by_code, Storage, MenuSystemItems, imágenes de ExampleCrud). Conviven seis mecanismos de registro de rutas y cinco patrones de controlador base.

Seguridad: ningún endpoint /api comprueba sesión ni rol (el parámetro `middleware` de `#[ApiRoutes]`/`#[ApiGetResource]` nunca se lee); consecuencias concretas: cambiar password/rol de cualquier usuario, registrarse como admin, truncar el menú o borrar objetos del bucket sin credenciales. El flujo de sesión mezcla Redis (fuente de verdad), Postgres (auth_user_sessions ya tiene todas las columnas), JWT (firmado pero nunca verificado), cookie HttpOnly (la única que el frontend usa) y localStorage (nunca leído); logout no revoca el refresh token, last_activity_at se guarda en el futuro por mutabilidad de Carbon, y todas las respuestas de auth son HTTP 200 por el bug statusCode/status_code. No hay inyección SQL en el área (Eloquent con bindings), pero sí fuga de `$e->getMessage()` en todos los catch, XSS reflejado en el placeholder de /component, validación de uploads dictada por el cliente y "lista vacía = todo permitido" en filtros. Cuatro formatos de JSON (msj/message/errors/error) y dos emisores (Response::json con die y Flight::json). Cero tests de auth/controladores; Response::json hace die, lo que los hace intesteables.

Veredicto: la idea (recurso declarativo por atributos + componentes PHP) entra en Lego 2; controladores y auth se reescriben enteros sobre Postgres con un solo router, un solo sobre de respuesta y auth obligatoria por defecto.

## Lecciones

- Los atributos PHP en el propio archivo del módulo (#[ApiGetResource], #[ApiRoutes], #[ApiComponent]) fueron la mejor decisión: cero registro manual y TableComponent alimentado directamente por el modelo. Lego 2 debe generalizarlo a un solo atributo de recurso que produzca API, tabla y formulario.
- Cada mejora se añadió sin retirar la anterior (routeMap.json → #[ApiRoutes] → #[ApiGetResource] → #[ApiCrudResource] → RestfulController): seis formas de registrar rutas. Regla para Lego 2: una nueva forma solo entra si borra la vieja en el mismo commit.
- La seguridad 'opcional' (parámetro middleware que nunca se lee, docblock 'sin auth para Postman') termina en todo abierto. Por defecto todo /api y /component exige sesión; lo público se declara explícitamente.
- Controladores que ejecutan en el constructor y responden con die/exit son intesteables: ni un test de login, logout o 401 en el repo. Devolver objetos Response y emitirlos en el kernel es lo que hace posible la capa de tests feature que el dueño pide.
- Para una sesión se usaron cinco almacenes (Redis, Postgres, JWT, cookie HttpOnly, localStorage) y solo la cookie hace trabajo real. Una cookie opaca + una tabla sessions en Postgres cubre login, renovación deslizante, logout y multi-dispositivo sin dependencias.
- La tabla auth_user_sessions ya tenía todas las columnas que Redis duplicaba; mover sesiones a Postgres es borrar tres métodos y añadir un índice, no un rediseño.
- Copias literales (login.js/automation.js, AbstractGet/AbstractCrud, normalizeId, formatBytes, el bloque try/catch+ResponseDTO en 25 acciones) aparecen cuando el núcleo no ofrece el helper: el sobre de respuesta, la validación y el CRUD deben vivir una sola vez en Core.
- Los módulos demo (ExampleCrud, Tools, Storage) acumulan versiones de la misma idea (tres mecanismos de imágenes). El ejemplo de referencia debe ser el caso mínimo que el núcleo genera, y se regenera, no se mantiene a mano.
- Devolver $e->getMessage() al cliente parece inocuo hasta que el mensaje es el SQL con bindings. El handler global de errores con código estable + log en servidor es infraestructura del día uno.
- Las convenciones permisivas ('lista vacía = todo permitido', 'constructor acepta cualquier $accion') son deuda de seguridad disfrazada de comodidad; la convención debe cerrar por defecto y documentarse con un test.
- Nombres mezclados (msj, accion, grup, isAutenticated, auth_grup_id) y typos en identificadores públicos se propagan al JS (10 archivos leen .msj). Código en inglés y un linter de nombres desde el inicio.

## Preguntas de diseño

- Sesión: ¿cookie opaca en Postgres sin JWT ni refresh token (renovación deslizante), o se necesita además acceso programático externo con tokens de API? Esto decide si el 'grupo api' existe en Lego 2.
- Autorización: ¿basta 'autenticado + rol SUPERADMIN' como hoy, o cada recurso declara permisos por acción (ver/crear/editar/borrar) por rol? ¿Los roles siguen en tabla editable o se declaran en código?
- Multi-dispositivo: hoy device_id está fijo en 1. ¿Una sola sesión por usuario (login invalida la anterior) o varias concurrentes con listado y cierre remoto?
- Escape explícito del CRUD declarativo: ¿(a) hooks en el modelo/recurso (beforeCreate, authorize, transform), (b) controlador que extiende al genérico y sobrescribe una acción, o (c) rutas extra con atributo? Elegir una sola.
- Uploads sin MinIO: ¿disco local bajo storage/ servido por PHP, o bytea/large objects en Postgres? ¿Límites de tipo y tamaño globales o por campo del recurso?
- Menú: ¿la estructura (ids, rutas, jerarquía) se declara en código/migración y la UI solo edita etiquetas, orden y roles, o la UI es dueña de todo (y entonces import/export/truncate se mantienen con auth y transacción)?
- Formato de error público: ¿código estable + mensaje en español listo para mostrar en la UI, o solo código y la UI traduce? ¿Se exponen errores de validación por campo en el mismo sobre?
- Estilo de API: ¿mutaciones por POST con JSON y acción en la URL (como hoy, compatible con el router actual) o REST con PUT/DELETE e id en la ruta? Afecta a CSRF, al router y a los componentes JS.
- Módulos abiertos: ¿se conserva /api/components/render (HTML de un componente PHP bajo demanda desde JS) como mecanismo oficial, o el servidor siempre devuelve pantallas completas por /component/{ruta}?
- Password del admin inicial y JWT/APP secrets: ¿se generan en `php lego init` y se imprimen una vez, o se exigen en .env sin default (el arranque falla si faltan)?
